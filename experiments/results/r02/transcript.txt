● I added the negative tests for POST /bookings in
  tests/api/bookings/create-booking-validation.spec.ts. The typecheck is clean,
  and all 18 booking tests pass against the local service (the new ones plus the
  existing create test).

  The file follows the same pattern as the existing user validation tests. Each
  test starts from a valid booking, changes one thing, and checks for a 400
  response with code VALIDATION_ERROR. It also checks that errors lists exactly
  the invalid fields, as the ticket requires. The tests don't check the message
  text, since the ticket says messages may change.

  Requests that should be rejected (14):
  - Dates:
    - checkIn missing, written as DD-MM-YYYY, or written with slashes.
    - checkOut missing or not a date.
    - checkOut on the check-in day or the day before it.
  - Guests: missing, 0, 9, -1, or 2.5.
  - Several errors at once: all three fields missing; and a same-day checkOut
    together with 9 guests. These check that there is exactly one error per
    invalid field.

  Requests that should be accepted (3): 1 guest, 8 guests, and checkOut one day
  after checkIn. These check the edges of the rules. Each booking they create is
  deleted afterwards.

  Two things the ticket doesn't specify, where I made a call:
  - Which field is blamed when checkOut isn't after checkIn: the tests expect
    checkOut. That's what the service returns today.
  - Order of the errors: the tests sort the field names before comparing, so
    they don't depend on the order the service lists them in.

  I didn't test guests sent as a string, such as "2". The request builder only
  accepts numbers, so that test would need a raw request.
