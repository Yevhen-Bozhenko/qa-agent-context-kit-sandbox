  3. Commands and results
  - npx playwright test tests/api/bookings/create-booking-validation.spec.ts,
    run three times: 8 passed each time, 0 failed, 0 flaky.
  - npm run typecheck: no errors.

  Which defect would make each negative test fail:
  - checkOut before checkIn: the API doesn't check date order at all, or allows
    checkOut earlier than checkIn.
  - checkOut equals checkIn: the check uses >= instead of >, so a same-day
    checkout is accepted. That breaks AC2.
  - guests = 0: the lower limit is missing or off by one (>= 0).
  - guests = 9: the upper limit is missing or off by one (<= 9).
  - checkIn missing: checkIn isn't treated as required, or extra fields are
    reported (for example checkOut too), which breaks the "exactly the invalid
    fields" rule in AC4.

  All five would also fail if the API returned a status other than 400 or a code
  other than VALIDATION_ERROR.

  4. Assumptions and unverified points
  - checkIn missing: I expect only ["checkIn"], as the task table says, even
    though checkOut is then present with nothing to compare against. AC4
    supports this reading but doesn't spell it out.
  - Cleanup in the accepted tests: they delete the booking straight after the
    201, as the users spec does. If an assertion failed first, the booking would
    not be deleted. The happy-path spec uses try/finally to avoid that; I can
    switch to it if you prefer.
  - I didn't check the delete response status, and the reference spec doesn't
    either.

  5. Suggestions for .ai/qa-context.md
  - Say which cleanup pattern to use for boundary-accept tests: a plain delete
    or try/finally. The two reference specs differ.
